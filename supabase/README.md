# Серверная часть Quaera

Приложение работает без сервера: прогресс лежит в `localStorage`, код
выполняется в браузере, аккаунт опционален. Supabase нужен ровно для двух
вещей, каждая из которых без сервера невозможна физически: **синхронизация
прогресса между устройствами** и **напоминания, когда приложение закрыто**.

Проект: `lueignziprnjnjiixdsh` (Франкфурт). Форку нужен свой — см. ниже.

## Что здесь лежит

```
migrations/
  0001_progress.sql            таблица прогресса, RLS, триггер updated_at
  0002_push_subscriptions.sql  подписки на push, RLS без политик
functions/
  push-subscribe/              приём и снятие подписки (зовёт клиент)
  push-send/                   рассылка подошедших (зовёт cron)
```

**`delete-account` в репозитории нет.** Она была выложена через редактор
дашборда раньше, чем завёлся этот каталог, и с тех пор существует только
там. Это долг, а не решение: форк, которому нужна кнопка удаления аккаунта,
её не получит. Восстанавливать — отдельной задачей.

CLI (`supabase link`, `supabase functions deploy`) в проекте не заводился:
функции выкладываются копированием в редактор дашборда. Для двух функций
это дешевле, чем тулчейн; если их станет больше — стоит завести.

## Развёртывание push с нуля

### 1. Миграция

`SQL Editor` → выполнить `migrations/0002_push_subscriptions.sql`.

Таблица закрыта наглухо: RLS включён, политик нет ни одной. Это значит
«никому ничего» — ни анониму, ни вошедшему. Трогают её только функции,
работающие под `service_role`, который RLS обходит. Довод расписан
в шапке самой миграции.

### 2. Ключи VAPID

Пара ECDSA P-256. Публичный обязан лежать в коде клиента открыто — браузер
передаёт его push-сервису при подписке. Приватный не должен попасть никуда,
кроме секретов функции.

Сгенерировать своими руками, без зависимостей:

```bash
node -e "const{generateKeyPairSync}=require('crypto');const{publicKey,privateKey}=generateKeyPairSync('ec',{namedCurve:'prime256v1'});const b=x=>Buffer.from(x).toString('base64').replace(/\+/g,'-').replace(/\//g,'_').replace(/=+$/,'');console.log('public :',b(publicKey.export({type:'spki',format:'der'}).subarray(-65)));console.log('private:',privateKey.export({format:'jwk'}).d)"
```

Публичный — в `src/push/client.ts` (константа `VAPID_PUBLIC_KEY`).
Приватный — в секреты проекта, шагом ниже.

### 3. Секреты функций

`Edge Functions` → `Secrets`:

| Имя | Значение |
| --- | --- |
| `VAPID_PUBLIC_KEY` | публичный ключ из шага 2 |
| `VAPID_PRIVATE_KEY` | приватный ключ из шага 2 |
| `VAPID_SUBJECT` | `mailto:` с рабочим адресом — требование спецификации |
| `PUSH_CRON_SECRET` | любая длинная случайная строка, её же в cron ниже |

`SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` Supabase подставляет сам —
вписывать руками не нужно и не следует.

### 4. Функции

`Edge Functions` → `Deploy a new function` → вставить содержимое
`functions/push-subscribe/index.ts` и `functions/push-send/index.ts`.

**У `push-subscribe` проверку JWT надо выключить.** Дашборд включает
«Verify JWT» по умолчанию, но этот гейт завязан на legacy-секрет и отсекает
запрос от клиента, который ходит ключом `sb_publishable_…`, ещё до кода
функции — на `delete-account` это уже стоило разбирательства. Проверять
здесь всё равно нечего: подписка анонимна по замыслу, а форму данных
функция проверяет сама.

**У `push-send` проверку можно оставить включённой:** её зовёт cron
с `service_role`. Сверх JWT она требует общий секрет в заголовке — без
этого любой обладатель publishable-ключа (он лежит в бандле открыто) мог бы
дёргать рассылку когда вздумается.

### 5. Расписание

`Database` → `Extensions` → включить `pg_cron` и `pg_net`. Дальше в SQL
Editor, подставив свои значения:

```sql
select cron.schedule(
  'quaera-push-send',
  '*/15 * * * *',
  $$
  select net.http_post(
    url := 'https://lueignziprnjnjiixdsh.supabase.co/functions/v1/push-send',
    headers := jsonb_build_object(
      'Content-Type', 'application/json',
      'Authorization', 'Bearer ВАШ_SERVICE_ROLE_KEY',
      'x-cron-secret', 'ВАШ_PUSH_CRON_SECRET'
    ),
    body := '{}'::jsonb
  );
  $$
);
```

Пятнадцать минут — не про точность, а про её отсутствие: момент пробуждения
наследует час, в который человек занимался (интервалы SM-2 целые в днях),
и опоздание на четверть часа в напоминании о повторении не значит ничего.
Чаще ходить незачем, реже — начнёт быть заметно.

Проверить, что задание живо: `select * from cron.job;`, история —
`select * from cron.job_run_details order by start_time desc limit 20;`.

### 6. Проверка живьём

Рассылку можно дёрнуть руками, не дожидаясь cron:

```bash
curl -X POST 'https://lueignziprnjnjiixdsh.supabase.co/functions/v1/push-send' \
  -H 'Authorization: Bearer ВАШ_SERVICE_ROLE_KEY' \
  -H 'x-cron-secret: ВАШ_PUSH_CRON_SECRET'
```

Ответ вида `{"sent":1,"gone":0,"failed":0}`. `sent` считает отправленные,
`gone` — удалённые мёртвые подписки, `failed` — отложенные до следующего
прогона.

Чтобы уведомление пришло сейчас, а не через двое суток, будильник можно
подвинуть в прошлое:

```sql
update push_subscriptions set wake_at = now() - interval '1 minute';
```

## Границы, которые стоит знать до того, как на это положатся

- **Подписка принадлежит устройству, а не человеку.** В таблице нет
  `user_id` и нет ссылки на `auth.users`: push работает без входа, иначе
  напоминание доставалось бы ровно тем, кто и так возвращается. Цена —
  занимался на другом устройстве, а будильник этого остался взведённым
  со старым числом.
- **Расписание считает клиент.** Сервер сравнивает отметку времени
  с `now()` и не знает ни паков, ни истории ответов. Довод —
  в `src/push/schedule.ts`: вторая реализация правила «что подошло»
  разошлась бы с `isDue` молча.
- **Текст уведомления собирает service worker**, сервер присылает только
  число. У того, кто добудет приватный ключ VAPID, нет способа показать
  произвольный текст от имени приложения.
- **На бесплатном тарифе бэкапов нет.** Потеря таблицы подписок не страшна
  (устройства переподпишутся при следующем открытии), потеря `progress` —
  страшна, и это отдельный незакрытый риск.
